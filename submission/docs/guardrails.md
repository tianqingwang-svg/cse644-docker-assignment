# Guardrails & Safety Policies for Autonomous CI Agents

This document defines the safety boundaries, access permissions, and human approval gates governing the AI CI Remediation Agent.

---

## 🛡️ Guardrail Principles

### 1. Zero Direct Autonomous Merges to Main
- The Remediation Agent is strictly prohibited from executing direct `git push` to protected branches (`main`, `master`, `release/*`).
- The Agent cannot merge Pull Requests automatically. All fixes must be opened as PRs on designated topic branches (`bot/fix-*`).

### 2. Mandatory Human Approval Gate
- In GitHub Actions, the `agent-remediate` job is locked behind the `agent-proposed` environment.
- The environment requires explicit approval from designated human reviewers before the job or downstream deployment can proceed.
- If unattended for over 60 minutes, the pipeline **aborts** automatically. It **never** auto-approves on timeout.

### 3. Least Privilege Principle (Token Scoping)
- The GitHub Token (`GH_TOKEN`) granted to the Agent has scoped permissions:
  - `contents: write` (to commit the fix branch)
  - `pull-requests: write` (to open the PR)
  - `admin: read-only` or `none` (strictly denied merge and administration rights)
- Branch protection rules enforce that PRs opened by the Agent cannot bypass mandatory human review.

### 4. Blast-Radius Limits
- **Scope Restriction**: The Agent is configured via system prompt to modify **at most 1 file** per invocation (the failing source file or `requirements.txt`).
- **Forbidden Files**: The Agent is explicitly instructed **NEVER** to modify:
  - Test suites (`tests/*.py`)
  - CI/CD configuration files (`.github/workflows/*`, `Jenkinsfile`)
  - Deployment manifests or secrets (`docker-compose.yml`, `.env`)
- If the Agent attempts to modify forbidden files, human reviewers will detect it via the mandatory PR checklist.

---

## 📋 Human Reviewer Checklist

Before approving any PR generated by the Agent, human reviewers must verify:
- [ ] The proposed change directly resolves the reported `root_cause` in `build_log.txt`.
- [ ] No extraneous code, refactoring, or stylistic changes are included.
- [ ] Test files and CI configuration files remain untouched.
- [ ] All new dependencies added to `requirements.txt` are safe, standard, and pinned appropriately.
